# 批量切片流水线：时间、故障与续跑

适用于一次处理 2 条以上素材。单条任务可以按 SKILL.md 的顺序手工走；批量必须按本文的约束做。

## 1. 时间模型：活跃时间 ≠ 墙钟时间

汇报和估算都要分开：

- **活跃计算时间**：ASR、建稿、导出真正占 CPU/GPU 的秒数；
- **墙钟时间**：从开始到交付的总时长，包含人工审片、等待、会话中断、机器休眠。

经验值（6 条、总素材约 35 分钟、1080×1920 源、540×960 预览）：

| 阶段 | 量级 | 说明 |
|---|---|---|
| ASR 对齐 | 约 0.3–0.5× 素材时长 | GPU 上 2–3× 实时；6 条约 7 分钟 |
| 删句/校字幕/写计划 | 0.5–1.5 分钟/条 | 需要逐条读上下文，不能省 |
| 建草稿 | < 10 秒/条 | 纯 JSON 复制/重算 |
| 导出 540×960 | 40–80 秒/条（3–6 分钟成片） | 与字幕数量、特效数量正相关 |
| 安装+校验 | 1–2 分钟/批 | 解密校验另算 |

给用户的 ETA 用**区间**，并说明是活跃时间；不要说“马上”。

## 2. manifest 与断点续跑

不要用“我记得已经做到哪了”驱动批量。每条素材一个状态文件：

```json
{
  "project": "<工程目录>",
  "items": [
    {
      "name": "03-示例",
      "source": "<源视频>",
      "stages": {
        "align":   {"status": "done", "out": "<aligned.json>"},
        "plan":    {"status": "done", "out": "<edl.json>"},
        "build":   {"status": "done", "out": "<draft 目录>"},
        "export":  {"status": "done", "out": "<mp4>"},
        "install": {"status": "pending"}
      }
    }
  ]
}
```

规则：

- 每阶段成功后立即写盘；重跑只做 `status != done` 的阶段。
- `export` 和 `install` 分开记录；导出成功不代表已安装。
- 恢复时先看 manifest、日志和文件 mtime；不要从第一条重跑。
- 日志至少记录：开始/结束时间、命令、退出码、输出路径、文件大小。

## 3. 路径与命令：禁止手拼

批量里最容易犯的低级错误是 shell 转义：

```bash
# 错误：反斜杠把 $ 转义，输出名变成 exports${n}.mp4
-o "D:\out\exports\${n}.mp4"

# 正确：用 Python 参数列表，或输出路径用正斜杠
subprocess.run([exe, "-ex", draft, "-o", str(out_dir / f"{name}.mp4"), ...])
```

要求：

- 统一用 `pathlib.Path` 拼路径，`subprocess.run([...])` 传参数列表，不经过 shell。
- 导出前检查目标路径不含 `$`、`{}`、`*`；导出后 `Path.exists()` 且大小 > 0，才进入下一条。
- 输出目录先清空或使用独立目录，避免旧文件冒充新文件。
- 如果必须用 shell，变量不要紧贴反斜杠；先 `echo` 出最终路径再执行。

## 4. 验收成本：结构校验优先，导出抽样

六条 540×960 全量导出约 6 分钟、约 500 MB，而且 headless 导出不认顶部模糊蒙版，预览会整帧糊。它适合做“第一条端到端”和“随机抽一条”，不适合当每条的必过关卡。

批量默认验收：

1. `check_preset.py` 对每条草稿 PASS（画布/倍速/调色/模糊/字幕/标题/转场贴纸）。
2. 字幕：0 重叠、每条 ≤ 11 字、0 空文本、起止不越界。
3. 事件：每个 `at` 必须落在某个 keep segment 内；输出时间不得为 0 或超出成片时长。
4. 工程：时间线顺序、`draft_content.json` 的 `id` 与 `project.json` 条目一致、时间线01未动。
5. 导出：第一条完整 `ffprobe` + `volumedetect` + `blackdetect` + 抽帧；其余抽 1 条。
   第一条还要跑一次 `verify_render_ab.py check`（同 EDL 去事件导对照），确认音效真的响、特效真的渲染——批量时最容易整批复制同一个"素材名写错/包缺失"的问题。
6. 用户重启剪映确认时间线可见；不要替用户声称“已显示”。

## 5. 已踩过的坑（按后果排序）

| 现象 | 根因 | 预防 |
|---|---|---|
| 导出文件叫 `exports${n}.mp4`，六条互相覆盖 | shell 中 `\$` 转义 | Python 参数列表；导出前打印并断言最终路径 |
| 第二条音效落在 0.0s | 事件时间在删除区间内，`map_time()` 返回 None 后被 `or 0` 吞掉 | 事件必须落在 keep segment；生成后断言每个事件 `inside` 且输出时间 > 0 |
| 字幕开头被吞、条数变少 | 删除区间向外扩 0.05s，吃掉了相邻保留句的开头 | 删除区间不要外扩；字幕起点落到删除区时吸附到最近 keep 边界（≤0.2s），否则丢弃并告警 |
| 同一时刻叠两条字幕 | 两条 ASR 行时间戳完全相同（重复识别） | 生成前按 `start` 去重；重复行整句删除 |
| 备份只剩 2 份 | 六次安装按“秒”命名，同秒覆盖 | 按微秒/序号命名，或整批前打包一次 `project.json` |
| 打开后顶部模糊变成全屏/消失 | 草稿 JSON 里的 `effect_mask` 还在，但 `Cache/effect/<effect_id>/<md5>` 的包缺失或放错 | 操作前后跑 `check_resources.py`；`missing: 0` 才继续；缺包用 `--fix-mask-cache` 按 effect_id/md5 从资源库下载，不要按 resource_id 盲复制 |
| 备份“完整”但恢复后渲染不对 | 只备份了 JSON，没有备份字体/特效/蒙版资源 | 备份包含资源清单和关键缓存包；先恢复资源再开剪映 |
| 六条全导完才安装，用户长时间看不到交付 | 验收顺序倒置 | 第一条端到端安装成功后，其余只做结构校验+抽样导出 |
| 4 小时无产出，误以为导出还在跑 | 会话/机器空转，日志和导出早已结束 | 心跳 + manifest；恢复时先查日志和文件 mtime，不重跑已完成阶段 |
| 删除率过低/过高 | 自动规则把重复句当内容，或把内容句当口吃 | 人工复核 plan.md 的删除清单与重复候选；目标 5–15% |

## 6. 恢复检查清单

中断后按顺序做，不要先重跑：

- [ ] 看 manifest：哪些阶段是 done；
- [ ] 看导出日志最后一行是否 `ALL_DONE`；
- [ ] 看产物 mtime/大小是否在中断前已封口；
- [ ] 看是否还有 `jy-draftc` / `ffmpeg` 进程；
- [ ] 只补 `pending` 阶段；
- [ ] 安装前重新备份 `project.json`（唯一命名）；
- [ ] 对每条草稿跑 `check_resources.py --content ...`，确认 `missing: 0`。
- [ ] 第一条成片跑过 `verify_render_ab.py check`，逐项 ✓（窗时间来自草稿段，不抄母带时间）

## 7. 复盘口径

没有直接日志时，不要断言“系统睡眠/应用挂起/网络问题”。只陈述可验证事实：

- 哪个时间点之后没有新文件；
- 日志最后一条是什么；
- 恢复时有没有残留进程；
- 哪些阶段已完成、哪些没有。

这次 6 条批量的可验证事实是：活跃约 23 分钟，12:54 六条导出全部完成；之后到 17:16 没有新产出，安装与校验在恢复后 2 分钟内完成。问题不在剪辑质量，在批量编排、进度反馈和验收顺序。
